# Firebase and Google Cloud Cost Audit — 2026-10-23

> **Status note (2026-11-02):** This PR carries only the Student Rewards teacher API read reductions (see the "Student Rewards" sections). Main already contains a Shorashim teacher listener fix (commit 97225643) and the Weekly Quiz teacher no longer bulk-downloads the audit/responses/completions roots, so the Shorashim and Weekly Quiz candidate changes described below were NOT brought over. The one thing still open for Shorashim is the duplicate startup read (one-shot reads followed by listeners that download the same data again); the old emulator measurement showed it would roughly halve teacher-page startup bytes. No database rules (`.indexOn`) are changed here.


## Executive finding

The strongest source-level candidate for avoidable Realtime Database egress is the **Shorashim Teacher full-scope listener** in `shorashim/teacher.js`. The original implementation listened with `on('value')` at `/posukPractice/shorashimLearning`; a student activity counter update could resend the entire subtree to every connected teacher. This draft replaces that parent listener with three scoped metadata listeners and student child events. Those listeners also provide the initial snapshots, so startup no longer reads catalog/settings/leaderboards and students once and then downloads them again when listeners attach.

The likely reduction is substantial when many teacher pages are open or student records contain long histories. Exact MB and dollars remain unknown without Cloud Monitoring/Realtime Database usage metrics and a production payload sample. No production tree was read for this audit.

## Measurements and cost limits

No connected Cloud Monitoring, Firebase usage, billing export, or Google Cloud metrics connector was available. Firebase CLI 15.26.0 is installed, but it does not provide authenticated production usage totals in this environment. Therefore:

- **Measured production MB/student or teacher session:** unavailable.
- **Measured monthly RTDB, Functions, or Storage cost:** unavailable.
- **Monthly savings in dollars:** cannot be calculated responsibly without the billing SKU, usage period, region, and measured bytes/invocations.
- **Emulator measurement:** A synthetic 24-student fixture transferred 891,582 bytes for the old four one-shot reads plus the parent initial value, and 445,788 bytes for the new scoped metadata values plus initial student events (50% less). The old one-shot roster read was 436,839 bytes, while child events totaled 436,862 bytes. A parent value event after one progress write was 445,817 bytes versus 18,202 bytes for the changed student child. Counts are UTF-8 JSON snapshot payload sizes from the local emulator, excluding WebSocket framing, compression, and protocol overhead; they are not production network meter readings.
- **Reproduction:** Install the repository dev dependencies, set `B3_RUN_RTDB_EMULATOR_TESTS=1`, then run `firebase emulators:exec --only database --project demo-shorashim-cost-audit "node --test tests/shorashim-teacher-roster-emulator.test.cjs"`. The `demo-*` project and in-test rules apply only to the local emulator.
- **Per-session estimate:** For this fixture, each active student with 9,600 progress writes/month (8 hours/day × 20 days × 60 writes/hour) accounts for ~4.28 GB/month at the former parent listener versus ~0.175 GB at the child listener. This is a synthetic scenario, not a production student-session measurement.
- **Monthly class scenario estimate:** With 24 active students each writing the two activity counters once/minute and one teacher page open for 8 hours/day and 20 days/month, the fixture implies ~102.7 GB/month at the former parent listener and ~4.2 GB/month with the scoped listeners. At $1/GB and a 10 GB/month no-cost allowance, the reduction is up to ~$93/month for this single class/teacher under those assumptions. Other project downloads can change the billable amount; real records, listener count, active time, and network accounting will change the bytes.
- **Pricing reference:** Firebase currently lists RTDB downloads at $1/GB after 10 GB/month at [Firebase pricing](https://firebase.google.com/pricing); billing documentation explains the downloaded-traffic metric at [Understand Realtime Database billing](https://firebase.google.com/docs/database/usage/billing). The estimate above uses that published rate and is not based on the project's bill.
- **Source-based model:** For actual changed student payload P MB, parent subtree S MB, N student updates, and T connected teachers, the approximate bytes avoided are `N × T × (S − P)`, plus avoided duplicate initial reads. Use measured usage graphs to supply S, P, N, and T.
- **Cost categories:** RTDB egress/storage, Cloud Functions invocations/compute, and Cloud Storage operations/egress are separate. Gallery image relocation shifts some bytes from RTDB to Storage; it does not make those bytes free.

To turn this into a cost model, export 30 days of Cloud Billing by service/SKU and collect RTDB downloaded bytes, storage bytes, and function invocation/latency metrics for the same interval. For page payload attribution, measure a synthetic representative tree in the emulator or use authorized browser network telemetry for a normal teacher session; do not read an entire live root merely to estimate its size.

## Candidate change in this branch

The draft replaces Shorashim Teacher's full-scope `value` listener with initial-plus-live `value` subscriptions at `SPACE/catalog`, `SPACE/settings`, and `SPACE/leaderboards`, plus child events at `SPACE/students`. ET/WT use listeners for authenticated assigned student IDs; they no longer fetch those records once and then subscribe to them again. Student changes update only the dashboard and are debounced; catalog, settings, and leaderboard changes redraw only their dependent views. New-class student records remain under that class's own `SPACE`. The emulator suite covers progress changes, adds/removals, ET/WT isolation, and authorized sign-in/reconnection. The change does not alter database rules, production data, or deployment configuration.

### Student Rewards scoped enrollment reads

`scopeFor()` previously called `syncClasses()`, which already reads each authorized class's `/studentRewards/enrollments/<classId>` node and adds newly synchronized members, then fetched the entire `/studentRewards/enrollments` root and filtered it to those same authorized classes. `syncClasses()` now returns those class-scoped enrollment snapshots, including newly added member IDs, and `scopeFor()` derives its student IDs from the returned data. The all-class enrollment read is removed without changing which authorized students are included.

- **Code/tests:** `backend/functions/rewards-teacher-core.cjs`; regression in `tests/rewards-teacher.test.cjs` asserts there is no top-level enrollment read and exactly one class enrollment read.
- **Instrumented mock-store read trace:** 30 unrelated classes × 20 synthetic students each: old all-class enrollment snapshot 13,979 B; current scoped sync reads the authorized class node once (4 B for an empty node), adds its two active workspace members to the in-memory scoped enrollment result, then persists those membership writes. The old root read is absent from the measured current `get()` trace. This measures JSON serialization in the mock store, not emulator wire bytes or Firebase billing.
- **Request count:** removes one broad enrollment-root read on each Rewards teacher API action while continuing to read each authorized class enrollment once as needed for sync.
- **Savings status:** Requires authenticated staging measurement to translate into actual RTDB downloaded bytes and billing impact. Do not attribute the fixture's 99% reduction to total teacher API traffic or project cost.

### Student Rewards duplicate student-root read

`syncClasses()` reads `/studentRewards/students` to map B3 IDs and create/reuse Rewards accounts. `loadRoot()` then fetched that same entire root again solely to select the already-known authorized student IDs. The synchronization snapshot now flows through `scopeFor()` into `loadRoot()` and is filtered once for the response. The API still returns only IDs enrolled in authorized classes.

- **Code/tests:** `backend/functions/rewards-teacher-core.cjs`; `tests/rewards-teacher.test.cjs` asserts exactly one `/studentRewards/students` read on load and checks unrelated students do not appear in the response.
- **Instrumented mock-store read trace:** With 600 unrelated fictional students, the synchronization root read is 84,748 JSON bytes before new Rewards accounts are created; the prior second full root read is removed, reducing full student-root reads on a `load` from 2 to 1. The API response contains only the two authorized students (351 JSON bytes). The mock records actual `get()` snapshot sizes and read counts; these are not emulator wire bytes or billing metering.
- **Combined test status:** Rewards tests passed 16/16 after adding multi-class and read-trace coverage. Enrollment fixture trace: 13,979 B old full-root snapshot avoided; 4 B authorized empty-class snapshot read, with the two active members added from authorized workspace membership.
- **Savings status:** Staging RTDB usage and whole-project cost reduction are still unmeasured; do not extrapolate the fixture bytes into the 50% project target.

### Student Rewards teacher authorization class reads

For a regular teacher, `teacherAccess()` previously downloaded `/b3Games/workspaces/b3-2026/classes` and filtered it to the teacher's assigned class IDs. It now reads the teacher assignment record first and fetches only those assigned class nodes, retaining the same active-class and `student-rewards` grant checks. The owner path still reads the full class root because it must discover every granted class.

- **Code/tests:** `backend/functions/rewards-teacher-core.cjs`; `tests/rewards-teacher.test.cjs` verifies no full root read for regular teachers, assigned nodes are read individually, ungranted assigned classes remain excluded, and owner class discovery still returns the granted class.
- **Request-count change:** For a regular teacher, one workspace-wide classes read is replaced with one read per assigned class. This narrows each snapshot to the teacher's authorized classes; actual byte reduction depends on the size of unrelated class records.
- **Savings status:** No representative byte measurement or staging usage measurement yet. The owner path remains unchanged.

### Rewards teacher steady-state scoped reads — 2026-11-01

`syncClasses()` previously fetched the complete `/studentRewards/students` node on every teacher API action so it could map B3 member IDs to Rewards IDs. It now uses the assigned classes' already-read enrollment nodes, fetches those enrolled student records directly, and checks deterministic IDs for new members. A full-root compatibility lookup still runs when an active member is not represented in scoped records; after that synchronization enrolls the account, subsequent refreshes use the scoped path. The class metadata snapshot read during sync is reused in the response, and class reward rounds are fetched by authorized class ID instead of downloading the rounds root and filtering it afterward.

- **Code/tests:** `backend/functions/rewards-teacher-core.cjs`, `tests/rewards-teacher.test.cjs`, and `tests/rewards-teacher-cost-emulator.test.cjs`. Mock regressions verify the initial student compatibility fallback, steady-state student lookup, and class-scoped class/round reads.
- **Local RTDB emulator measurement:** with two enrolled synthetic students and 40 unrelated classes, the old measured roots total 91,956 B (`students` 84,909 B, `classes` 3,960 B, `classRewardRounds` 3,087 B). The current targeted snapshots total 341 B (two student records 214 B, authorized class metadata 70 B, authorized round node 57 B). These three roots' decoded JSON bytes fell 99.63% in this fixture; full-root reads for all three paths are absent on the measured steady-state request. This excludes other API reads, wire framing/compression, production traffic, and billing.
- **Full serial Rewards/Shorashim test sweep:** 83 tests, 83 passed, 0 failed, 0 skipped with the local RTDB emulator enabled. The cache-version assertions validate script presence/load order independent of cache token; the Perek-choice VM fixture supplies the existing follow-screen guard. `git diff --check` passes.
- **Savings status:** 99.63% applies only to these three fixture subtrees, not all endpoint bytes or project costs. New/legacy account synchronization can still trigger a student-root fallback; staging frequency and actual RTDB downloaded-byte metrics remain unmeasured.

### Point-request / adjustment query candidate not adopted — 2026-11-01

The teacher API also reads the full `/studentRewards/pointRequests` and `/studentRewards/pointAdjustments` roots before filtering to authorized students. A local RTDB emulator experiment queried each student ID with `orderByChild(...).equalTo(...)`, but the emulator emitted Firebase warnings that the fields had no `.indexOn` and “data will be downloaded and filtered on the client.” The returned subset size therefore does not prove reduced database egress, so that code change was removed. Enabling the required production indexes would modify RTDB rules and needs separate owner approval; no rules were changed. These two broad history reads remain an open cost candidate.
