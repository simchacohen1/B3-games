## 3. The two rules bugs in #147 (fixed on the verification branch)
1. `firebase-rules.hardened.json` lacked #124's `b3Private` block, so a teacher got `PERMISSION_DENIED` writing `b3Private/classPointerSharePermissions/...` and could not start a class.
2. The `resources` node was never closed, so `access`, `toolGrants`, `name`, `active`, `siteEnabled`, `posukPracticeLimit`, `halachaAccess` sat at `classes/$classId/resources/...`; a signed-in student could read only `members/<me>`, the home page showed "No activities are available" and its live class watcher threw.
Re-verify any new #147 head with: start the lab from that checkout (`scripts\pointer-lab\start-lab.cmd`) and run `node scripts/pointer-lab/verify-rules.cjs` (must print 25 of 25), then `check-share.cjs`.

## 4. Safe deployment sequence (each step approved separately; do not skip the checks)
**Step 0, before anything:** (a) export the Realtime Database (Firebase console > Realtime Database > three dots > Export JSON) and store it outside the repository; (b) copy the currently live database rules text from the console into a file (this is the rollback file); (c) note the live `classPointerShareAuth` revision (Google Cloud console > Cloud Run > `classpointershareauth` > Revisions); (d) confirm the synthetic class "Pointer Test" (teacher + two students) exists and no real class is used for the live check; (e) record the exact commit SHA to deploy.
**Step 1, backend function only** (Command Prompt, not PowerShell, from a clean checkout of that SHA, after `npm --prefix backend/functions ci`): `firebase deploy --only functions:classPointerShareAuth --project b3-games`. Never `--only database` or hosting here, never `funTorahTeacherClaim` or `funTorahManageStudents`. **Optional and separate:** `cleanupClassPointerShareTickets` is a scheduled function (it creates a Cloud Scheduler job, a possible small new charge after the free jobs); skip it for the first release, tickets expire by themselves, and approve it separately. Smoke: an anonymous POST with a valid-format unknown room returns 403 "Class Pointer is not active for this class". Expected effect on the current website: none (old pages use `issue`/`verify`, which keep working; students with only the old shared default passcode can no longer share a screen).
**Step 2, database rules, additive only:** deploy #124's `firebase-rules.json` (adds the `classPointerSessions` write rule and the `b3Private` block; reads stay as they are today). **WARNING: on any checkout that contains #147, the default `firebase.json` selects the HARDENED rules, so a plain `firebase deploy --only database` would switch the public reads off before Pointer is verified. Do not use it for this step.** Instead: save the live rules text from the console to `live-rules.json` (outside git), run `node scripts/rules-additive-check.cjs live-rules.json`; it must print `OK` (it fails on any changed or removed rule and on any addition outside `b3Private` and `classPointerSessions`). Then deploy explicitly: `firebase deploy --only database --config firebase.pointer-additive.json --project b3-games` (that config selects `firebase-rules.json` only).
**Step 3, website:** merge #124 to `main` (GitHub Pages publishes automatically, about a minute; use Ctrl+Shift+R). Do this only after steps 1 and 2 are confirmed, because the new teacher page writes the private permission rows.
**Step 4, live check with the synthetic class (owner + assistant):** teacher starts; Student A and B join (names come from the server); a stranger who knows the room id is refused (assistant can try with the lab-style script); teacher shares a browser tab and switches to it (students still see it moving); Student A shares Entire Screen and the teacher sees it, also after Student A moves between pages; teacher turns screen sharing off for B (B's share stops within a minute); end and restart; no unexpected 403 in the teacher or student pages.
**Step 5 (separate release, later): hardened rules (#147 with the two fixes).** Only after Step 4 passes and the new pages are live and cached. Deploy the hardened rules explicitly with `firebase deploy --only database --config firebase.json --project b3-games` (the default config selects `firebase-rules.hardened.json`; the Step 0(b) file is the rollback), then re-run the Step 4 checks plus: student home shows class name and tool tiles, a teacher sees only own classes, a stranger cannot read `b3Games/students` or class lists, Game Show/Weekly Quiz/Shorashim/Posuk Practice/Rashi/Chazara/Gematria open for a synthetic student. This is the step most likely to break an existing page, so keep the previous rules file ready and watch for "Please sign in again" locks.

**Known Step 5 blockers found by offline analysis on 2026-10-17 (these do NOT affect Steps 1-4 / the Pointer release; they must be resolved or consciously accepted before the hardened rules are deployed).** The existing emulator tests check single-node reads, not the list reads the pages really make, so these were not caught:
1. **Rashi Letters multiplayer ("Looking for friends"):** `rashi-letters/student.html` (lines ~1353, ~1369-1372, ~1444) reads and listens to the WHOLE `rashiLetters/matchRooms` node. The hardened rule only allows reading one room (`matchRooms/$room`) of the student's own class, so the list read is denied and the room listener is cancelled: matching, offers and live room updates would stop working. Solo Rashi practice is unaffected. Fix options (do not weaken the rule): class-scoped room path (`matchRooms/$classId/$room`) with the page reading only its own class, or a backend function for matchmaking.
2. **Shorashim class match leaderboard:** `shorashim/app.js` (lines ~267 and ~273) reads and listens to the whole `posukPractice/shorashimLearning/leaderboards/match` node; the hardened rule allows only `leaderboards/match/$pairCount/$studentId` for the student's own row (or a teacher of that student's class). The `once` read is in try/catch so the page keeps working, but the leaderboard would silently be empty. A parent-level read cannot be class-filtered, so the real fix is a per-class leaderboard path, or accept an empty leaderboard.
Both findings come from `scripts/pointer-lab/verify-rules-offline.cjs` plus reading the page code; confirm in the lab with `check-pages.cjs` against the hardened rules.

## 5. Rollback (fastest first)
- **Function:** Cloud Run console > `classpointershareauth` > Revisions > send 100% of traffic to the revision noted in Step 0(c) (instant). Or redeploy the previous commit with the same single-function command.
- **Database rules:** paste the text saved in Step 0(b) into Firebase console > Realtime Database > Rules and press Publish (instant, no command needed; do NOT use the default `firebase deploy`, which selects the hardened file). Rules changes do not touch data.
- **Website:** revert the merge commit on `main` in GitHub Desktop and push (Pages republishes in about a minute).
- **Data:** nothing in this release rewrites existing data; tickets and permission rows expire or are removed when a lesson ends. The Step 0(a) export is the safety net.
- Rollback order if the live check fails: website first (if pages misbehave), then rules, then function.
