## Read-only Storage CORS verification

The image URL generated by the existing submission handler is a tokenized `https://firebasestorage.googleapis.com/v0/b/.../o/...?...` download URL. For this anonymous image request, the successful image response must permit the page's origin (`Access-Control-Allow-Origin` with the matching origin or `*`). Images served from a different endpoint may have different CORS requirements.

Official references checked on October 21, 2026:

- [Firebase browser download and CORS guidance](https://firebase.google.com/docs/storage/web/download-files#cors_configuration).
- [Cloud Storage CORS endpoint behavior](https://docs.cloud.google.com/storage/docs/cross-origin#cloud-storage-cors-support): JSON and XML endpoints apply CORS differently, so generic advice to change bucket configuration is not proof this endpoint needs a change.

Read-only probes used a deliberately nonexistent synthetic filename in the existing bucket, with origins `https://funtorahtools.com` and `https://www.funtorahtools.com`:

| Request | Both origins | Response CORS |
|---|---|---|
| OPTIONS requesting GET | HTTP 200 | `Access-Control-Allow-Origin: *`, GET allowed |
| HEAD on the nonexistent/unapproved probe path | HTTP 403 | `Access-Control-Allow-Origin: *` |

No response body, object listing, real artwork, or private record was read. Raw response headers are in `repair-evidence/storage-cors-probes.json`. This establishes endpoint CORS responses on preflight/error paths, not a successful production artwork download. It does not read or verify the bucket's private `cors` metadata. No production configuration change is justified by these probes alone, and none was attempted.
